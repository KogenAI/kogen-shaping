Shape must refuse acceptance steps that cannot finish within the 120 s per-step approval limit. Readiness runs on the unchanged tree, where a whole-suite step can fail fast and conceal its runtime after implementation. The original reported incidents and reproducing command source are preserved in acceptance.feature, including Studio issue kogen/e05fb12c-082a-415f-973c-22b1bad2ce86. Do not try to reproduce a two-minute timeout to establish a static rule.

Refuse whole-test-suite commands in step code while continuing to allow a single test file, package or named test. Keep all other static checks unchanged. The current tree already has the detector, its step-selfcheck and check_package wiring, and focused rejection/narrowing regressions; retain those rather than replacing them or adding a second detector. The remaining policy gap is that the shaper contract does not explicitly state the 120 s acceptance-step limit. Add that instruction, including refusal despite fail-fast unchanged-tree readiness and narrowing whole-suite commands to targeted tests. Add focused regression coverage for the delivered instruction; the new acceptance also guards the existing detector through real Shape submissions. (evidence: shape/steplimit.go; shape/steplimit_test.go; shape/stepcheck.go; shape/checkpackage.go; shape/prompts/shaper.md)

The static rule is a source check, not an elapsed-time predictor or a new timeout mechanism. Preserve its existing handling of command strings, argument lists, wrappers, test runners, narrowing flags and used step definitions. Do not change the approval limit, configured project checks, unrelated static checks, or gate scheduling. No new flag, configuration option, setting or environment variable is introduced. The independent acceptance harness supplies source guarded by an unconditional throw; no submitted test command actually runs. The fixture's readiness runner replays a local report; that proves submission/check wiring, not the historical runtime.
