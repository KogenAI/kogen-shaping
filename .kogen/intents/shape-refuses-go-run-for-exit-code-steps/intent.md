# Refuse go run in exit-code step definitions

Slug: shape-refuses-go-run-for-exit-code-steps
Model: not applicable — a stateless text check of step definition source
Acceptance:

- features/steps/shape-refuses-go-run-for-exit-code-steps__driver/harness_test.go.txt

The Shape step self-check (stepSelfcheck in shape/stepcheck.go) refuses a step definition that asserts the exit code or the stderr of a program it runs through go run (also npm run and npx where the same exit-code rule is stated in the prompt), with one `exit_code` line per offending step definition naming the file, the step definition and the fix (compile first with go build, then run the binary). The refusal is held exactly like an undefined step; nothing is published. Steps that use go run only for output or to start something, steps that run a compiled binary, and go run text in comments or in strings that nothing executes stay accepted. The check is deterministic text analysis: no model call, no setting, no flag. The prompt text, the step language, the existing self-check results and messages and every published artifact format are unchanged. Only shape/stepcheck.go and a test file of the shape package change.

The verification module's verify.StepItems already produces one `exit_code` item per step file (verify.ExitWrapper) for a body that mentions go run and an exit status. The change refines those items inside stepSelfcheck, directly after verify.StepItems: for each `exit_code` item it re-judges every definition of that file on its body with comments removed. A definition is judged only when its body calls a process-running function (a name containing spawn, exec, fork, system, shell, run, command or cmd followed by an opening parenthesis). A body in which a line mentions stderr together with a comparison (assert, expect, ===, ==, .includes(, .match(, toContain, toMatch, toBe, toEqual, .test( ) asserts stderr and is judged like a body that mentions an exit status. Each offending definition gets its own item with the existing wording; a file without an offending definition keeps an ok item.

## Source comparison
- Refuse go run with an exit code assertion, one line naming file, step and fix: addressed; the existing exit_code line is kept and acceptance asserts its exact text (source: request).
- Refuse go run with a stderr comparison: addressed by the refinement; acceptance asserts the same line (source: request).
- One line per offending step: addressed; acceptance asserts two lines for a file with two offending definitions (source: request).
- Accept compiled-binary steps, go run for output only (including reading stderr without comparing it), go run in comments and go run in a string no call executes: addressed; acceptance covers each (source: request).
- Existing fixtures keep their results and messages: addressed by keeping the wording and by running the existing step-check tests (source: request).
- Readiness still starts alongside the cheap gates and the prompt text is untouched: unchanged, no acceptance check observes readiness (source: request).
