# Check required request literals before approval

Slug: k-shape-request-literal-coverage
Model: not applicable — one stateless check per checked submission maps the literal-check model's items to statuses, an event and feedback lines; no retained state, retry or interacting rule is added beyond the existing submission attempts
Acceptance:
- .kogen/intents/k-shape-request-literal-coverage/acceptance.feature
- features/steps/k-shape-request-literal-coverage__steps.js
- features/steps/k-shape-request-literal-coverage__harness.js

Request (kogen-shaping, "Preserve required request literals through shaping"). Problem: a request can specify exact non-secret inputs needed by an implementation or example, yet an otherwise ready Intent can summarize them without their values. The builder then has to guess values it cannot recover from the Intent. Guidance to preserve the values does not itself establish that the submitted package carries them. Need: at the existing shaping and approval boundary, compare the supplied request and settled answers with the complete proposed Intent and acceptance for explicitly required non-secret literal inputs and examples. Return actionable feedback identifying an omitted or changed required value and its source, so the package can be corrected before approval. Keep source material private and respect its authority; do not invent values, make informal context binding, expose secrets, or claim coverage when an original is unavailable. Preserve legitimate differences between a literal that must be exact and descriptive text that can be paraphrased. Synthetic acceptance: (1) a request explicitly requires a registration example using `/demo_one` and `/demo-two`; a candidate that says only "register both repositories" receives feedback identifying both missing values; a corrected package carrying both exact values proceeds through the normal checks. (2) A candidate that substitutes `/demo-one` for `/demo_one` is flagged; an unrelated descriptive paraphrase is not. An explicitly superseded value is not demanded as the current value. (3) A required value supplied in a settled answer is checked against the same candidate. An unavailable original is reported as unknown, not treated as an empty request or a successful comparison. Secret material is neither copied into the package nor exposed in feedback. (4) A complete candidate with the specified literals remains eligible for normal approval; feedback does not silently alter files or approve the Intent.

Current state of the code: Shape's `checkSubmission` (shape/shape.go) runs the carried-decisions gate, the evidence gate and the decision check (shape/decision.go, one model call that compares the candidate intent.md's Decisions with the request text only), then the step self-check and readiness. Nothing compares the request or the answers with the acceptance or step files, and nothing checks that an exact value the request requires appears in the package. The shaper policy already asks the shaper to preserve settled non-secret literals; that guidance stays as it is.

After this change, `kogen intent shape` (packages `shape` and `cmd/kogen-shape`) runs a literal check on every files submission whose decision check found no problem, before the step self-check, for the native shaper and for a claude-code shaper, with no option, flag, setting or environment variable. A model lists the literal values that the request and the settled answers explicitly require; Kogen itself verifies that each listed value is copied from its source, decides secret, superseded, informal and unverifiable values, and compares each remaining value with the complete candidate package byte for byte. A required value that the package does not carry exactly refuses the submission with feedback naming the value, its source and, when the package carries a substitute, that substitute. A complete package goes on to the existing checks unchanged and is published exactly as submitted, eligible for the normal `kogen intent approve`; the check never edits a file and never approves. When the original request is not available, the check reports unknown and compares nothing.

Out of scope and unchanged: Refine and Approve (neither runs the literal check); the decision check, question check, contract review and every other gate; every prompt under shape/prompts, `ShaperInstructions`, the Refine prompt, the shaper and Refine tool definitions and the policy and force goldens (shape/testdata/*golden*.json), byte for byte; go.mod and go.sum; kogen-coordinator; this repository's `.kogen/project.yaml`; and the files of earlier Intents.

## Decisions
- Placement: in `checkSubmission`, after `decisionCheck` returns no feedback lines and before `kogen: checking step code`; it runs on every files submission that reaches that point, including a corrected one, and makes exactly one model call (or one claude-code session) per run of the check. (evidence: shape/shape.go; shape/decision.go) (source: request)
- The original request is unavailable when the shaping's request text (`sh.request`, from state.json) is empty after trimming whitespace. Then the check makes no model call, records `{"event":"literal_check","status":"unknown","reason":"the original request is not available"}`, prints the progress line `kogen: request literal check unknown: the original request is not available; required literals were not compared` (through `sh.progress`, so with its usual ` (<n> s)` suffix), refuses nothing and lets the submission go on to the step self-check. It never records a compared event for such a submission. (evidence: shape/shape.go) (source: request)
- Sources: `request` is the request text; `answer <n>` is question n of the latest round of the shaping state's rounds, the numbering the shaper already cites; `round <r> answer <n>` is question n of an earlier round r (counted from 1). An answer's source text is its resolved answer: an answer that is a single letter a-z selecting an existing option of its question is that option's label, any other answer is the text as given. An unanswered question is no source. (evidence: shape/context.go) (source: request)
- The check's user input is exactly `Slug: <slug>\n\n# Request\n\n<request>\n\n# Answers\n\n<answers>\n\n# Candidate package\n\n` followed, for each package file in order, by `## <path>\n\n<content>\n\n`. `<answers>` is one line per answered question, `round <r> answer <n>: <resolved answer>` for earlier rounds in round and question order, then `answer <n>: <resolved answer>` for the latest round, joined by newlines; it is `(none)` when there is no answered question. The package files are, as written to the checkout after the fixers: the Intent's intent.md, its acceptance.feature, its model file when `Model:` names one, then every other `Acceptance:` path in its listed order, each once. (evidence: shape/decision.go; shape/context.go) (source: request)
- Native route: one provider request through the shape role with the literal instructions, one user message and exactly one tool, `submit_literal_check`, in its own conversation (`startConversation(sh.ev, "literal-check")`, call label `literal check`). It prints `kogen: checking the required literals` and then `kogen: literal check response <usage> wall_ms=<n>`, and its usage is added to the summed usage of Shape's usage line. claude-code route: one fresh read-only executor session per check (`startExternal`, directory `<evidence dir>/executor-literal-<n>`) with the instructions plus the input as its brief and the schema as its structured result; its rounds are added to the round count of the usage line. (evidence: shape/decision.go) (source: request)
- `submit_literal_check` takes a strict schema `{"items": [item]}`. Each item has exactly these required fields: `literal`, `source`, `source_quote`, `package_value`, `why` (strings) and `status` (`required`, `superseded`, `informal` or `secret`); `additionalProperties` is false. A payload that is not such an object fails with class `shape`, reason `literal_check_invalid` and the detail `the literal check answer is not a valid submit_literal_check payload (<why>); nothing was published` (exit 1); so does a native answer without exactly one `submit_literal_check` call. (evidence: shape/decision.go) (source: request)
- The instructions tell the model it sees the request, the settled answers and the complete candidate package; that it lists every literal value the request or a settled answer explicitly requires, with its source written `request`, `answer <n>` or `round <r> answer <n>`; that descriptive wording is not a required literal; and that `package_value` is the value the package uses in its place, empty when there is none. They end with `Answer by calling submit_literal_check.` and contain these four sentences verbatim, each on its own line. First: `A required literal is a value that the request or a settled answer explicitly requires the implementation or an example to use exactly, such as a path, command, name, identifier, number or example input; descriptive text that may be paraphrased is not a literal.` Second: `Give status superseded for a value that the request or a later answer explicitly replaces, and status secret for secret material such as a password, token, key or credential; for secret material leave literal, source_quote, package_value and why empty.` Third: `Copy each literal exactly as its source writes it, with source_quote copied exactly from that source and containing the literal; Kogen itself compares each literal with the package byte for byte.` Fourth: `Give status informal for a value that appears only in informal background, an aside or an example the source marks optional; Kogen never demands an informal value.` (evidence: shape/decision.go) (source: request)
- Kogen's rules for each item, in this order; "found" means an exact byte substring, with case, punctuation and whitespace kept. (1) The item's source text is the request for `request`, the resolved answer for `answer <n>` or `round <r> answer <n>`, and none otherwise. (2) The item is `secret` when its status is `secret`, when the redactor changes its literal, or when its literal is found in its source text but not in the redactor's rendering of that source text. The redactor is `verify.NewRedactor(<the session's environment>, <HOME>)`, the one Shape already builds. (3) Otherwise it is `unverified` when its literal is blank, it has no source text, its source_quote is not found in the source text, or its literal is not found in its source_quote. (4) Otherwise a `superseded` item stays `superseded` and an `informal` item stays `informal`. (5) Otherwise (status `required`) it is `present` when its literal is found in the content of any package file; `changed` when not, and its package_value is not blank, differs from the literal and is found in a package file; else `missing`. Only `missing` and `changed` items are problems; `superseded`, `informal`, `secret` and `unverified` values are never demanded, so informal context is never binding. (evidence: shape/decision.go; shape/shape.go) (source: request)
- Feedback: with at least one problem the submission is refused (`sh.refused("literal_check", <problem lines>)`, an invalid outcome, no file changed) and the shaper receives, joined by newlines: the headline `Literal check: <n> required literal values are not carried exactly by the package; copy each value byte for byte into the Intent or its acceptance where the Intent uses it (descriptive text may stay paraphrased), or restore the substituted value:`, then one line per problem in item order. A missing problem is `literal: <literal> | source: <source> | source_quote: "<source_quote>" | status: missing | why: <why>`. A changed problem is `literal: <literal> | source: <source> | source_quote: "<source_quote>" | status: changed | package_value: <package_value> | why: <why>`. Every text taken from an item is passed through the redactor before it is shown or recorded. With no problem the submission goes on to the step self-check and readiness unchanged. (evidence: shape/decision.go; shape/shape.go) (source: request)
- Event: each compared check records `{"event":"literal_check","status":"compared","present":<n>,"missing":<n>,"changed":<n>,"superseded":<n>,"informal":<n>,"secret":<n>,"unverified":<n>,"items":[...]}`. Each item that is not secret is recorded as `{"literal","source","source_quote","status","package_value","why"}` with its final status and redacted texts; a secret item is recorded only as `{"source":<source>,"status":"secret"}`, never with its literal, quote, package value or reason. (evidence: shape/decision.go) (source: request)
- Test doubles: the fake provider in shape/helper_test.go answers a request that offers `submit_literal_check` with `{"items": []}` by default (through `contractWire` when set), keeps such requests out of `requests()` and `rawRequests()` like decision check requests, and a `route` answer takes precedence over that default. The scripted executor of shape/lineup_shape_test.go answers literal sessions (schema containing `"source_quote"`) with `{"items": []}` by default, outside its counted shaper rounds, as it does for decision sessions. (evidence: shape/helper_test.go) (source: request)
- The acceptance harness relies on these existing test helpers keeping their names and signatures: `newShpFx`; the `shpFx` fields `Root`, `Stdout`, `Stderr` and `Prov` and its methods `setReport`, `shape`, `exists` and `read`; the `shpProvider` field `route` and method `allRequests`; and `shpStep`, `shpAnswer`, `shpCall`, `shpSubmit`, `shpUI`, `shpToolNames`, `shpOutputs`, `shpBody`, `contractKind`, `decisionRequest`, `SubmitQuestionCheckTool`, `shpScopedIntentMD`, `shpFeature` and `shpSteps`. Tests are synthetic only, with no live provider, and use only owned child processes and temporary folders. (evidence: shape/helper_test.go) (source: request)

## Source comparison
- Addressed, Need "compare the request and settled answers with the complete proposed Intent and acceptance": the literal check input carries the request, every resolved answer and every package file (intent.md, acceptance.feature, model, Acceptance step files); Kogen's rule (5) compares against all of them (scenario "The literal check reads the request, the answers and the whole candidate package").
- Synthetic acceptance 1 (`/demo_one`, `/demo-two`; "register both repositories" gets feedback naming both; the corrected package proceeds): case `omitted`, Decisions line `- The README example registers both repositories. (source: request)`, corrected to `- The README example registers /demo_one and /demo-two. (source: request)`.
- Synthetic acceptance 2 (`/demo-one` substituted for `/demo_one` is flagged): case `substituted`, status `changed` with `package_value: /demo-one`; `/demo-two` is not flagged. Descriptive paraphrase not flagged: case `complete` ("in a welcoming tone" for the request's "Keep the wording friendly.") publishes from its first submission. Superseded value: `/demo_old` is recorded `superseded` and not demanded.
- "do not make informal context binding": case `informal` adds the background line "For background only, an old prototype once used /legacy-demo; it is not part of this change."; the model reports `/legacy-demo` as `informal`, Kogen records it `informal`, demands nothing and publishes from the first submission; the instructions carry the fourth sentence.
- Synthetic acceptance 3: a value from a settled answer (case `answer`, answer `1: The example uses port 7443`, literal `7443`, source `answer 1`); an unavailable original (case `unknown`: state.json loses its request before the answering run) is recorded unknown with no model call and no compared event; secret material (case `secret`, a synthetic `password: ...` line) is recorded only as a secret count and is absent from feedback, events, stdout, stderr and the published intent.md.
- Synthetic acceptance 4: case `complete` publishes the submitted intent.md byte for byte, prints `Next: kogen intent approve is-even` and writes no approval.
- "do not invent values": rule (3) drops an item whose literal or quote is not copied from its source (case `complete`, `/demo_three` recorded `unverified`).
- "existing shaping and approval boundary": the check runs inside Shape before publication, so every Intent Shape publishes for approval has passed it or recorded unknown; Approve and Refine stay unchanged, as for the decision check.

## Tests
- Kogen's per-item rules (present, missing, changed, superseded, informal, secret by status and by the redactor, unverified for a blank literal, an unknown source, an unfound quote and a literal outside its quote, exact byte comparison so `/demo-one` does not match `/demo_one`), the counts, the headline and both problem line formats, and redaction of echoed text: add TestLiteralOutcomeRules in shape/literal_test.go (unit)
- Source resolution (letter answer to option label, typed answer as given, `answer <n>` for the latest round, `round <r> answer <n>` for an earlier one, unanswered question is no source, `(none)` without answers) and the exact input layout with the package file order: add TestLiteralCheckInput in shape/literal_test.go (unit)
- The payload parser rejects a missing or mistyped field, an extra field and an unknown status with shape/literal_check_invalid: add TestParseLiteralCheck in shape/literal_test.go (unit)
- The instructions carry the four verbatim sentences and end with `Answer by calling submit_literal_check.`: add TestLiteralInstructions in shape/literal_test.go (unit)
- A claude-code shaper runs one fresh literal session per checked submission with the schema and gets the feedback lines: add TestExternalShapeLiteralCheck beside the decision check case in shape/lineup_shape_test.go (integration)
- A native Shape makes one literal check request per checked submission, refuses with gate literal_check on a problem, records unknown without a request when the request is unavailable, and publishes a complete package unchanged: acceptance harness cases; existing native tests keep their assertions through the fake provider's default answer (integration)
- The request's synthetic cases end to end through `Shape` with a scripted literal-check model: acceptance.feature (scenario)
- Prompts, tool definitions and goldens stay byte-identical: the existing policy and force golden tests pass unchanged (existing)
