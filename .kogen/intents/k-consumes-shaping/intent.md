Slug: k-consumes-shaping
Model: not applicable — the change adds test suites and their READMEs; kogen-shaping's behaviour and state are unchanged

Kogen's repositories depend on each other through Go modules (kogen vendors kogen-loop). Each repository keeps a contract/ suite for what it provides, but nothing states what a consumer relies on, so a producer's landing has to build and test every consumer in full (the blanket consumer check), which is slow and misses uses no test exercises. The owner's rule is two-sided contracts: each repository also states, as tests, exactly what it consumes. kogen-shaping gains one suite per Kogen dependency, each stating exactly what kogen-shaping relies on from that producer:

- `consumes/kogen-coordinator/`: what kogen-shaping relies on from kogen-coordinator (module `github.com/KogenAI/kogen-coordinator`).
- `consumes/kogen-executor/`: from kogen-executor (module `github.com/KogenAI/kogen-executor`).
- `consumes/kogen-loop/`: from kogen-loop (module `kogen-loop`, which go.mod replaces with `github.com/KogenAI/kogen-loop`).
- `consumes/kogen-verification/`: from kogen-verification (module `github.com/KogenAI/kogen-verification`).

The suites pass at the versions go.mod pins now. Nothing else changes: `shape/`, `cmd/`, `go.mod` and `go.sum` stay byte for byte as committed at HEAD, no command, flag or option is added (the only `main` package outside `features/` stays `github.com/KogenAI/kogen-shaping/cmd/kogen-shape`), and kogen-shaping's behaviour is the same. `README.md` may gain one bullet naming `consumes/` in its Packages list; nothing else in it changes. This checkout has no `contract/` directory at HEAD; this Intent neither creates nor requires one (see Source comparison).

### What a use is

kogen-shaping's own code is the non-test Go files of the packages of module `github.com/KogenAI/kogen-shaping` outside `contract/`, `consumes/` and `features/` (today `shape` and `cmd/kogen-shape`). A use of a producer is every identifier in that code that resolves (go/types `Uses` or `Selections`) to an exported package-level object of a package of the producer's module, named `pkg.Name`, or to a method or field of one of its named types, named `pkg.Type.Member` by the type that declares the member (a promoted member by its declaring type). `pkg` is the last element of the package's import path. The acceptance observer, the Go program whose source `features/steps/k-consumes-shaping__observer.js` exports, computes exactly this and prints it with `-list`:

```sh
d=$(mktemp -d) && node -e "process.stdout.write(require('./features/steps/k-consumes-shaping__observer.js').source)" > "$d/main.go" && printf 'module observer\n\ngo 1.27\n' > "$d/go.mod" && (cd "$d" && GOFLAGS= GOWORK=off go build -o observer .) && "$d/observer" -list . kogen-coordinator=github.com/KogenAI/kogen-coordinator kogen-executor=github.com/KogenAI/kogen-executor kogen-loop=kogen-loop kogen-verification=github.com/KogenAI/kogen-verification
```

### Each suite

- One Go package in `consumes/<producer>/` made only of `_test.go` files (package name `consumes`), plus `README.md`. No non-test Go file, no subpackage, no build constraint, no `t.Skip`, no sleep.
- Written only against the producer's exported API. It imports only the standard library (never `net` or any `net/...` package), the producer's packages, and packages of the other three Kogen dependency modules only where a producer signature needs their values (for example `git.Repo` values passed to `project` functions, or `project.Config` given to `verify.Readiness`). It never imports a package of kogen-shaping (`shape`, `cmd/kogen-shape`) or any other module, uses no unexported or internal package (`kogen-loop/internal/...`), and adds no go.mod requirement.
- Every use in its list is named by at least one of its tests, and asserted so that changing what kogen-shaping relies on fails the suite: the type or signature of each function, method, type, field and constant pinned at compile time with its types written out (for example `var _ func(*os.File) error = durable.Sync`), and, through real calls, the behaviour, values and formats kogen-shaping's call sites in `shape/*.go` and `cmd/kogen-shape/main.go` depend on (for example the bytes `project.EncodeJSON` produces for the maps shape writes, `project.Hash` of a baseline in a `t.TempDir()` checkout changing when a baselined file changes, `project.LoadConfig` of a `.kogen/project.yaml` written in `t.TempDir()`, `project.LoadIntent`/`project.CheckIntent` of an Intent package written there, `project.ParseGherkin` and `project.ParseStages` of small inputs, the paths of `project.IntentDir`, `IntentMDPath`, `FeaturePath`, `ModelPath`, `ApprovalPath` and `ConfigPath`, the `git.Repo` methods on a Git repository made in `t.TempDir()`, the class, reason, detail and exit of the stops made by `sys.Fail`, `executor.Fail` and `executor.RoundLimit`, the role and ending constants `executor.RoleShape`, `executor.EndFinish`, `executor.ReasonProtocol` and `executor.ReasonUnavailable`, the value of `tools.InputBudgetBytes` equal to `provider.InputBudgetBytes`, `tools.Measure`/`tools.Cut` results, `provider.Usage.Add` and `Line`, and `thinking.Strip` of a sample). A method of an interface (`executor.Executor`, `executor.Session`) counts as covered only when a test names it through the interface (a call on an interface value or a method expression), not by implementing it in a fake. A use that cannot run without the network, a model, a signed-in harness, the `claude` CLI or host-installed Node, Cucumber or Quint (`provider.Client.Respond` sending, `provider.RequireLogin` with real credentials, `executor.ClaudeCode` starting a session, `executor.Executor.Start` of a real executor, `tools.DocumentationTool` fetching, `verify.Readiness.Gate` running acceptance, `verify.RunStepScript`) is pinned by its signature and by the offline outcome kogen-shaping's call relies on where the producer documents one (for example `provider.RequireLogin` refusing as it documents (`provider/login`, exit 4) for a fresh `HOME` without a login, or the Node, Quint and Cucumber paths `verify.ToolsFromInstall` resolves under an install root in `t.TempDir()`). - Each assertion message names the inventory item it checks (for example `t.Errorf("project.Hash: ...")`).

No network (no listener, no HTTP server, no fixed port), no host paths (every file under `t.TempDir()`; no read of kogen-shaping's sources, the module cache or another repository's files), no shared state between tests; deterministic under `-race -count=1 -shuffle=on` and `-trimpath`.

### Acceptance

The observer, run on the checkout, must print `ok`: each suite exists, has no non-test Go file and no forbidden import, its tests name every use, and its inventory equals its list. `go list ./...` must list the four consumes packages (so the normal `go test ./...` runs them), and `go test -count=1 ./consumes/...` must pass with an `ok` line (not `[no tests to run]`) for each; `go test -race -count=1 -shuffle=on ./consumes/...` must pass the same way with a Git dir, work tree and index that do not exist, a fresh `HOME` whose `.gitconfig` signs every commit and tag with a key that does not exist, `GOPROXY=off` and `GOFLAGS=-mod=readonly -buildvcs=false -trimpath`. The whole-repository `go test ./...` is the configured `go-test` check (`GOFLAGS=-trimpath go test ./...`), which verification runs in full; the acceptance steps do not rerun it, and none of their subprocesses has a time limit of its own (only Cucumber's step timeout of 900 s, 300 s for the HEAD and main-package checks). `features/steps/k-consumes-shaping__fixtures.js` holds known-good observer controls (bare references of every use, without tests), not the implementation: the Build writes real tests and does not copy them.

## Decisions
- One suite per Kogen dependency, `consumes/<producer>/`, written only against the producer's exported API with the isolation stated under "Each suite" (source: request)
- The suites are written in the style the request asks for (compile-time pins with their types written out, assertion messages naming their inventory item, a README with an inventory); no automatic step observes style, so it needs human evaluation by the reviewer, and no scenario claims it (source: request)
- Whether each test asserts the behaviour kogen-shaping relies on, beyond naming the use, needs human evaluation by the reviewer; the acceptance observer checks only that every use is named by a test and listed in the inventory (source: request)
- A suite asserts exactly what kogen-shaping's non-test code uses of its producer, and its README inventory lists those uses, checked by a go/types listing of the imported identifiers per dependency (source: request)
- The suites run in `go test ./...` at the pinned versions; no behaviour change, no new command, flag or option, go.mod and go.sum unchanged (source: request)
