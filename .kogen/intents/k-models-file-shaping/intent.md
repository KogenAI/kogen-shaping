K-MODELS-FILE-SHAPING, the consumer-first half of K-MODELS-FILE (filed by kogen-delivery, 3 Nov 2026). kogen-coordinator's K-MODELS-FILE (green candidate 2a4c69a, Build b04dd3bd, not on kogen-coordinator main yet) moves the model lineup out of `.kogen/project.yaml`: package `project` reads the team lineup from `.kogen/models.yaml` (a per-machine `.kogen/local/models.yaml` overrides it role by role), refuses a `.kogen/project.yaml` that still has `models:` with `environment/models_moved: .kogen/project.yaml still has models:; move that lineup to .kogen/models.yaml` (exit 3), and `Baseline` lists `.kogen/models.yaml` right after `.kogen/project.yaml` whether or not it exists. Its landing check (3 Nov 04:32Z) runs kogen-shaping's tests against it, and they fail: shape.TestClaudeLineupShapeSubmission (shape/lineup_shape_test.go:253, an index-out-of-range panic), TestWorkersReceiveBoundedLongLineReadsAndReplayTheDeliveredDisplayExactly, TestBatchAnExistingEditableStepIsAValidDraftTarget, TestBatchOwnershipAndBoundaryRefusalPrecedesCallsAndNeverAltersTheRawIndex and TestShapeBatchInterruptCancelsEveryJob. kogen-build has the paired half (K-MODELS-FILE-BUILD).

After this change kogen-shaping works with the lineup in `.kogen/models.yaml` as K-MODELS-FILE reads it and stays green against the kogen-coordinator version go.mod pins today (lineup still under `models:` in `.kogen/project.yaml`). It lands first, on its own; the coordinator change follows. go.mod and go.sum keep the pinned coordinator. The K-MODELS-FILE change outside tests is the protected fixture `features/steps/testdata/k_models_file_shaping/coordinator.patch` (the reference `git show 2a4c69a` diff of project/baseline.go, project/config.go and project/render.go, verbatim).

## Current behavior (observed in scratch copies outside the checkout)
- Production reads the lineup only through `project.LoadConfig` (`cfg.Models`), so Shape and Refine take the moved lineup from the coordinator unchanged; a scratch run of Shape against the K-MODELS-FILE coordinator selected the Claude Code shape role written in `.kogen/models.yaml`.
- On the unchanged tree with the K-MODELS-FILE coordinator about 60 tests of `./shape` fail, for four reasons: (1) fixtures put `models:` into `.kogen/project.yaml` or into `project.ParseConfig` text (`lineupShapeConfig` in shape/lineup_test.go, `useExternalShape` and the workers case of TestClaudeLineupUnsupportedCapabilities in shape/lineup_shape_test.go, `chatWire` and `anthropicWire` in shape/force_wires_test.go, `shpAnthropic` in shape/shape_test.go) and get `environment/models_moved`; (2) `refFx.pkg` (shape/refine_test.go) reads every baseline path and fails on the absent `.kogen/models.yaml`; (3) the batch fixture brief (shape/batch_test.go, `protected_paths: [".kogen/project.yaml", "guard.txt"]`) omits `.kogen/models.yaml`, and `shape_batch` refuses a brief whose `protected_paths` leave out any baseline path; (4) TestApproveCardOutput expects a Files list without `.kogen/models.yaml`.
- Production defect under K-MODELS-FILE: the shaper's protection contract (`contextBlocks`, shape/context.go) keeps only `.kogen/project.yaml`, Acceptance paths and Intent files from the baseline, so it never names `.kogen/models.yaml`. A shaper that lists the contract's paths as a `shape_batch` brief's `protected_paths` has every batch refused.

## Production change (shape/context.go only)
- In the "# Protection contract" block, "automatic paths currently present or listed" keeps every baseline path that is `.kogen/project.yaml`, `.kogen/models.yaml`, an Acceptance path or a file under the Intent directory, in baseline order, rendered with `InspectStrings` as today.
- When the baseline contains `.kogen/models.yaml`, the definition line is exactly `` automatic baseline: every file in `<Intent directory>/`, every path listed under the Intent's `Acceptance:` (including step files), `.kogen/project.yaml` and `.kogen/models.yaml`. `` Otherwise it stays exactly `` automatic baseline: every file in `<Intent directory>/`, every path listed under the Intent's `Acceptance:` (including step files), and `.kogen/project.yaml`. ``
- Example: Shape of slug `is-even` in a project without `protect` matches gives, against the K-MODELS-FILE coordinator, `automatic paths currently present or listed: [".kogen/project.yaml", ".kogen/models.yaml"]` (also when `.kogen/models.yaml` does not exist, since the baseline lists it), and against the pinned coordinator today's `automatic paths currently present or listed: [".kogen/project.yaml"]`. Against the pinned coordinator every prompt byte is unchanged.
- Name the path with a literal `".kogen/models.yaml"` (for example a shape-package constant): the code must build against the pinned coordinator, which has no `project.ModelsPath`, `ParseModels`, `ModelSources` or `ModelsTemplate`. Nothing else in production changes: no new command, flag or environment variable, no timeout, limit or retry change, no go.mod or go.sum change, no README change.
