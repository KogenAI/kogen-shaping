Implement K-SHAPE-PROMPT-MOVE (kogen-delivery owner plan of 3 Nov 2026, split-speed item 2) in kogen-shaping. Own the Shaper prompt, context guidance and submission tool definitions here and run shaping from those copies. Do not change kogen-executor, its pin, any prompt or schema bytes, CLI, commands, flags or timeouts. Removal of executor's unused copies belongs to a separate follow-up.

## Decisions
- Preserve all existing model-visible text and tool wire format, including names, descriptions, schemas, strictness, optional fields and tool order. No user-facing behavior changes. (source: request)
- Preserve normal shaping, worker-enabled shaping and external shaping submission schemas. Generic file/search/documentation tool definitions can continue to come from kogen-loop. Refine, init, builder and reviewer policies remain outside this move. (source: request)
- A Shaper policy edit must be possible, checked and compared in this module alone, without an executor edit, re-pin or release. (source: request)

Technical settlement: copy the source prompt templates, context guidance and shared passages they consume into embedded files under shape/prompts/. Keep template expansion byte-compatible. Keep the existing Shape-owned named-test, unwritten-test and runner-observer suffixes unchanged. Move the definitions used for probe, propose_files, submit, shape_batch and worker_result into shaping, including the readiness acknowledgment text consumed by submit. Do not merely forward these definitions to agent.Defs. Provide ShaperToolDefinitions(names ...string) []map[string]any in package shape, preserving the requested order and generic-tool dispatch; use this same callable interface for actual shaping requests, worker requests and the external submit parameter schema. This small callable interface is the acceptance boundary, not a new CLI. Keep unrelated executor usage intact.

Add a committed golden and a test in shaping covering complete ShaperInstructions and ordered model-facing tool definitions for default shaping, workers enabled and worker tool sets. Generate the golden mechanically from current pinned executor v0.0.0-20261102193603-1aea0728c24b plus the existing shaping suffixes, not from hand-authored expectations or from the new implementation. Use deterministic JSON serialization for wire objects and compare its complete bytes, including prompt whitespace and final newlines, rather than only hashes or selected fields. Retain provenance and a reproducible generation path under the existing Go test -update convention, without a new command or flag. Ordinary tests must not silently rewrite the golden. The baseline remains an independent executor-derived oracle when local policy changes. Prove that the provider request actually uses the local copies, not a parallel unused copy; use the existing scripted-provider shaping and worker fixtures. A focused local-policy mutation test must demonstrate that a local prompt or submit-schema edit reaches the captured request and produces golden drift without modifying the dependency.
