Fix K-STEP-FILE-COLLISION in kogen-shaping. Outside agents shape and build several Intents of one repository in separate Git worktrees, then land them one after another by merge or rebase. Concurrent shaping must produce exclusive step files and exclusive step bindings, not accidentally approve whichever definition arrives first. Do not add a command, flag, option, provider integration, shared-worktree lock or cache isolation mechanism.

The reproducer supplied with the request was Kogen de2b21b, 30 October 2026 17:33–17:41Z: a tiny Go repository, two worktrees, Claude Sonnet medium, similar requests, the same chosen step-file name and overlapping step text. Each worktree worked alone. After landing one and moving the second onto it, the second approved package listed the first Intent's step file, silently mixing definitions. Per-worktree `.kogen/local/`, concurrent Shape/Build, shared Go cache and TMPDIR were not the failure. Studio `kogen/worktree-parallel-builds` parked point 3 tracks this problem; parallel builds are the owner's priority. Historical provider, timing and repository details identify the report, not a requirement to make live paid calls or revive that old revision.

## Contract

1. Give newly shaped step artifacts an Intent-specific namespace before any candidate is published or approved. Use the slug as the stable discriminator, not a worktree path, basename chosen by the model alone, random working-directory identity or landing order. For new Intents use files under the configured steps directory named `<slug>__<suffix>.js` (nonempty suffix), and step sentences/definitions scoped by the literal prefix `<slug>: `. Explain this convention in shaping and refinement context and actionable submission feedback. It keeps a flat steps glob working without changing project configuration. The acceptance examples use `alpha__steps.js` / `alpha: ` and `beta__steps.js` / `beta: `.
2. Enforce ownership, not merely prompting. Validate proposals, their Acceptance lists and actual step bindings. A newly shaped/refined package cannot adopt, overwrite, import or rely on another Intent's step artifact or definitions. A generic shared filename or unscoped new definition is a correctable invalid submission, not a published candidate. Reject ambiguous or foreign bindings, including overlapping definitions in different files. File ownership alone does not establish definition isolation; a scoped filename containing the other Intent's text must fail. Do not require renaming unchanged old packages as a migration.
3. Before approval or approval refresh, detect new cross-Intent sharing and mixed dependencies on the current tree, including a clean, already-resolved merge or rebase (not just unmerged Git index entries). Check before generic stale-hash handling can obscure the collision and before publishing/refreshing approval. Refuse with nonzero status and diagnostic detail naming the conflicting Intent slugs and step file paths. A path reused by two Intents names that path and both slugs; overlapping text in two files names both files and both slugs. Preserve previous approval bytes and Git HEAD on refusal. Detect from repository packages plus existing approval evidence, not solely ephemeral state of the other worktree.
4. Preserve the 3 November 06:14Z delivery decision: existing approved Intents already sharing a file remain usable while their approved dependencies are unchanged. Existing sharing is not permission for a third/new approval or refinement to adopt that file. Any changed/mixed approved step dependency after merge/rebase is refused; unchanged grandfathered sharing is not blanket permission to edit shared steps. Legacy approvals lacking new metadata must remain readable and usable; do not invent a new approval CLI or require re-shaping them merely to upgrade. The old exported `project.Approval` format is an acceptance fixture for this compatibility boundary. Preserve normal source custody, readiness, explicit approval, obsolete-contract handling and protection rules.
5. In two worktrees started from the same commit, Shape may run at the same time. Both corrected, exclusive packages must be approvable independently; merging or rebasing either one onto the other preserves both approved packages' bytes, and the second worktree can perform the normal existing approval revalidation. There is no coordination between their local approval directories. Refusing every second Intent is not a fix. The synthetic acceptance runner uses real Cucumber and keeps `app.txt` red so readiness and post-move reapproval exercise legitimate missing-feature red, not the unrelated already-passing-on-new-base rule.
