# Run minimal witnesses for wrong controls

Slug: k-shape-controls-minimal-witnesses
Model: not applicable — one deterministic run plan and judgement inside the existing wrong-implementation check, with no state that outlives a check
Acceptance:
- .kogen/intents/k-shape-controls-minimal-witnesses/acceptance.feature
- features/steps/k-shape-controls-minimal-witnesses__steps.js
- features/steps/k-shape-controls-minimal-witnesses__harness.js

In the AoR C7 qualification, shaping reaches readiness only 3 of 5 times. Task 1 exceeds the 1800 second cell deadline before its first shaper submission. Task 5 runs only 6 of 8 full Rails acceptance controls within the 300 second controls budget. The cause: the wrong-implementation check (`shape/controls.go`, `controlsLines`) runs the candidate's complete acceptance once for the correct implementation and once more, complete, for every wrong implementation of controls.json, so its cost is runs times the cost of the whole feature, and generating the controls grows the first round. Studio kogen issue 9e78ee95-d6a7-4884-a8ee-5ba2c146a85d asks for correct and wrong controls to be qualified inside the existing 300 second controls budget and 1800 second cell deadline, without raising either, using scenario-specific minimal correct and wrong witnesses and a single full correct guard per exact candidate, keeping the exact target-step assertion evidence, and leaving the final Build verification gates unchanged.

After this change, for a candidate with N controls (N wrong implementations):
1. The correct implementation is run once against the whole feature. Its run is the full guard: every checked property must pass with it, as today, and a failure there ends the check before any wrong run, as today.
2. Each wrong implementation is run once, against only its witness (Decisions D1). The witness run reports only the witness scenarios, and the judgement of that wrong implementation reads only them.
3. The judgement keeps its rules 2 to 5 for the witness: the witness must fail, at the target step, with an AssertionError thrown by a step file the Intent lists under Acceptance, after the earlier steps of the scenario passed. A wrong witness that passes its target scenario, fails it at another step, fails without an assertion or fails with an assertion thrown outside the step files is still refused, with the same refusal lines as today. The rule that the wrong implementation must leave every scenario of the other checked properties passing is removed (D2).
4. The `wrong_implementation_check` event records the target step and assertion evidence of every control that was run (D3).
5. The run cap (8 runs, so at most 7 wrong implementations), the 300 second total time cap, the progress lines (`kogen: wrong-implementation check: run <i> of <n> (...)`, n = 1 + wrong implementations), the setup commands per run, the refusal lines of the unchanged rules, and every Build verification gate stay as they are (D4).

Nothing else changes: no prompt or policy golden, no timeout or budget constant, no configured command.

## Source comparison
- Addressed: "qualify correct and wrong control behaviour inside the existing 300s controls budget and 1800s cell deadline, without raising either timeout". Changes 1 and 2 cut the wrong runs from the whole feature to their witness; change 5 and D4 keep both limits. Acceptance scenario 4 pins the run cap and the 300 second figure through the harness's refusal headline and run-cap refusal. The 1800 second cell deadline is outside this checkout and is not touched.
- Addressed: "Use scenario-specific minimal correct and wrong witnesses, and run a single full correct guard per exact candidate". Change 1 is the single full correct guard; change 2 and D1 are the witnesses. The correct implementation is not narrowed: its single run covers the whole feature so that every scenario of every checked property is proved passable. Acceptance scenario 1 observes the scenarios each run executed: the whole feature once, then only the target scenario (the example rows of an outline) per wrong implementation.
- Addressed: "Keep the exact target-step assertion evidence"; "the qualification result still records the exact target step and assertion evidence for each control". Change 3 keeps the judgement; change 4 and D3 record the evidence per control. Acceptance scenario 2 requires the recorded step, failed step, assertion first line and step-file location for a clean check, a failure at an earlier step and a witness that did not fail.
- Addressed: "a test shows that a wrong witness that does not fail its target step is still rejected". Acceptance scenario 3 requires the refusal lines for a witness that passes its target and one that fails at an earlier step. The new Go tests do the same through the fake runner.
- Addressed: "no timeout or budget constant changes" and "Final Build verification gates stay unchanged" (change 5, D4); "the repo's full test suite is green" through the configured go-test check (existing).
- Conflicting, resolved: the request keeps the target-step assertion evidence but its witness runs cannot show the scenarios of other properties, so the old rule 6 is dropped (D2). The shaper prompt (`shape/prompts/shaper.md`) says only that Kogen runs the controls within the existing 300 second cap, which stays true; no prompt or policy golden changes.
- Omitted: raising any timeout, reusing one prepared copy across the runs (setup commands still run per run) and changing how controls.json is generated are not requested.

## Tests
- The correct implementation is run once against the whole feature and each wrong implementation only against its witness (the example rows of an outline included): new tests in `shape/controls_test.go` using `controlsReal` and its fake runner, which fail on the unchanged code because every wrong run executes every scenario; acceptance scenario 1 (integration)
- A wrong implementation is judged on its witness alone, so one that also breaks another property's scenario is not refused for it: a new `shape/controls_test.go` test and the replaced rule 6 subtest of `TestControlsJudgeAll`; acceptance scenario 1 (integration)
- The event records the target step, failed step, assertion first line and step-file location of each control, empty fields when the witness did not fail, and `[]` when no wrong implementation ran: new tests in `shape/controls_test.go`; acceptance scenario 2 (integration)
- A wrong witness that does not fail its target step (it passes, fails at an earlier step, fails without an assertion or asserts outside the step files) is still refused with today's lines: new tests in `shape/controls_test.go` through the fake runner; acceptance scenario 3 (regression)
- The run cap, the 300 second time cap, the progress lines and the refusal headline's caps are unchanged: the existing `TestWrongImplementationCaps` and `TestControlsRefusalJoinsContractRefusal`; acceptance scenario 4 (existing)
- The whole suite stays green: the configured go-test check (existing)

## Feasibility
- These are scratch runs from this read-only external session, not Kogen probe records. With go1.27.2 and Node v24.21.0, the harness Go source of `features/steps/k-shape-controls-minimal-witnesses__harness.js`, compiled into the shape tests through `go test -c -vet=off -overlay`, passed in 5.3 s on the unchanged tree. It showed every run executing both scenarios, `controls` absent from the event, and for the target-scenario-only case the two `also fails scenario ... which exercises another property` lines: that is the red the feature expects to turn green. A scratch implementation of the change (the controls.json correct implementation) passed all 4 scenarios, 14 steps, in 6 s. Each of the 4 wrong implementations of controls.json failed exactly the one scenario and the step it names, with an AssertionError thrown by the step file.
- The installed Cucumber, run on a feature with a plain scenario, an outline with two examples and a second plain scenario, selected exactly the scenario for its line, exactly one example for an Examples row line, both examples for the outline line, and the union for two lines (`file:9:11`), each with exit 0 and a complete message report.
- The observer controls run the step file's judgments on known observations. Good: the values of every Then step of the feature, with the real `-test.v` output of the harness run. Bad: the unchanged tree's observation as a whole and its cases, a failed, unfinished, failed-test, skipped, doubled, empty and observation-less harness run, a missing case, and every leaf of every compared value changed, dropped or extended.
