# Apply Shape's acceptance checks to Refine

Slug: k-refine-acceptance-gates
Model: not applicable — each check is a stateless judgment of one checked candidate; Refine reuses its existing bounded submission loop and Shape's existing per-package contract memory, adding no workflow state
Acceptance:
- .kogen/intents/k-refine-acceptance-gates/acceptance.feature
- features/steps/k-refine-acceptance-gates__steps.js

`kogen intent refine` (`Refine`, shape/refine.go) must refuse a refined draft for the same reasons, and with the same feedback to the shaper, as `kogen intent shape` refuses a shaped one. Today `(*refine).check` runs the candidate's readiness (`r.scratchD.Check`) with no readiness `Gate` and never calls the contract check. Only Shape installs the gate (`sh.rd.Gate` in `(*shaping).shape`) and calls `contractCheck` (`(*shaping).checkSubmission`). So a refinement can publish a draft that Shape would refuse. After this change, every one of Shape's acceptance checks also applies to each candidate Refine checks, and a candidate that passes them publishes exactly as today. Only kogen-shaping changes. Shape's checks, their order, texts and events stay unchanged, and so does Shape itself. No command, flag or setting is added, and no timeout or bound is raised: the unpassable control keeps `verify.StepTimeout`, the contract conversations keep 8 requests and 32 tool calls, and the submission retry limit stays 3.

### The checks
These are Shape's acceptance checks, reused as they are:
1. The unwritten-tests gate (`unwrittenTestsGate`).
2. The runner-observer gate (`runnerObserverGate`), judged only when no scenario has an unwritten test (`readinessGate`).
3. The unpassable-step check (`unpassableGate` with its control run), only for a readiness result with a failed scenario.
4. The contract check (`contractCheck`): the independent read-only review and, for findings Kogen evidences, the confirmation. Both refusal kinds count, confirmed contradictions and confirmed environment findings.

### Where they run in Refine
- Checks 1 to 3 run as the readiness gate of every candidate readiness check that Refine runs in its scratch checkout, in Shape's order, before any readiness evidence is recorded. The unpassable control materializes the candidate tree (`ready.CandidateTree`) from the scratch checkout's repository. It uses the readiness tools, else `KOGEN_NODE` and `KOGEN_CUCUMBER`, and stays fail-open exactly as in Shape.
- They do not run on the original draft's own readiness (`originalReadiness`, retained or checked in scratch). The original is observed, not judged, so a draft that fails a check can still be refined. As today, a candidate whose readiness inputs are unchanged from an already checked result (`Current`) is acknowledged without a new check. This includes an unchanged submission of a red original, which publishes the original bytes as today.
- Check 4 runs after a candidate's fresh readiness check has passed checks 1 to 3, whether the result is red or green, as in Shape. Its package hash is `project.Hash` of the candidate's baseline in the scratch checkout, the hash `kogen intent approve` would show. A hash already checked clean in this run is not reviewed again. A hash already refused in this run is refused again with the same feedback before readiness runs, with no new review. An acknowledgment runs no new readiness and no contract check.
- The review sees the candidate as Shape's does: the candidate intent.md, its acceptance.feature, and the step files the Intent lists that this run proposed. It also gets the readiness observations of that check (`All scenarios pass now.` when green). Contract quotes are evidenced against the candidate's intent.md, or against HEAD for files the run did not propose. A native refiner uses the same review and confirmation conversations as Shape, with the shape role's provider route. An external refiner (`executor: claude-code`) uses the same fresh read-only external sessions as Shape. An incomplete contract check lets the candidate go on, as in Shape.

### Refusal
- The `submit_refinement` output for a refused candidate is exactly the text Shape returns to its shaper for that refusal: `unwrittenTestsError.text()`, `runnerObserverError.text()`, `unpassableError.text()` or `contractFeedback(confirmed)`. Nothing is prepended or appended: no `not ready:` prefix and no retained-proposals sentence. For the same refined draft and the same readiness and contract answers, Refine's text equals Shape's byte for byte.
- A refusal counts as an invalid submission against the existing retry limit. The refused submission's well-formed proposals stay accumulated, as for any not-ready submission. The refused candidate's readiness result is never kept as observations to acknowledge. Nothing is published. The draft's files, hash, approval, source receipt and `.kogen/local/readiness/<slug>.json` stay unchanged, and no `contract-contradictions.json` record is written. `diagnostic-<n>.txt` in the refinement evidence holds the refusal text.
- At the limit, Refine ends with the existing `shape/refinement_invalid` error "no valid ready correction after 3 submissions; the original draft is preserved" (exit 1). Its lines are the last refusal text split at newlines.
- The checks record their existing `unpassable_check` and `contract_review` events, with Shape's shapes, in the refinement evidence's `events.ndjson`.

### Unchanged
- Refine's plain route: a refinement that passes every check publishes after exactly the refiner requests it makes today, with the same output lines and result. The contract review and confirmation are their own read-only conversations, as in Shape. They are not requests of the refiner's conversation, and the refiner gets no extra request.
- Red acknowledgment, topology, ownership, fixer and publication rules; the external refiner's feedback route; approval revocation and receipts.
- The force goldens `shape/testdata/force_ordinary_golden.json` and `shape/testdata/force_ordinary_models_golden.json` stay byte-identical; do not regenerate them. Existing Refine tests whose provider speaks another wire answer the contract review on that wire through `Prov.contractWire`, as `forceOrdinary` already does for Shape.

## Decisions
- Refine refuses a refined draft for the same reasons as Shape refuses a shaped one, with the same feedback to the shaper: every acceptance check Shape applies before publishing also applies to Refine's result. (source: request)
- A refinement that needs no refusal keeps working with no extra request to the refiner. (source: request)
- Shape's checks and feedback stay unchanged; no command or flag is added and no timeout is raised. (source: request)

## Source comparison
- Addressed: the Problem. `(*refine).check` sets no readiness gate and makes no contract or unpassable check. Now Refine applies the readiness gates, the unpassable-step control and the contract check to each candidate it checks (see "Where they run in Refine").
- Addressed: Need 1, same reasons and same feedback. Each acceptance journey sends one refined draft to native Shape, as a whole submission, and to native Refine, as the correction of a ready draft, with a scripted shaper. Refine's feedback must equal Shape's feedback for that draft. The journeys are `unwritten`, `observer`, `unpassable` (with a real Cucumber runner), `contract` (a confirmed contradiction) and `environment` (a confirmed environment finding), in features/steps/k-refine-acceptance-gates__steps.js. Each also checks the exhaustion error, the unchanged draft and readiness record, and that Refine's contract requests match Shape's (one review and one confirmation in the two contract journeys; the identical second and third submissions are refused without another review).
- Addressed: Need 2, the plain route. The `plain` journey publishes a green refinement after one refiner request. The `red` journey publishes an ordinary missing-feature red refinement after the usual acknowledgment (two refiner requests). The `repair` journey publishes a corrected draft after an unwritten-tests refusal in the same run. The force goldens record the refiner's requests and stay byte-identical.
- Interpretation: "no extra model request" means no extra request in the refiner's conversation. The contract check is itself one of the checks the request requires Refine to apply. Like Shape, it is a separate read-only review (plus a confirmation only for evidenced findings) for each freshly checked candidate. The force goldens and the test provider's `requests()` already exclude those conversations.
- Interpretation: "every check Shape applies before publishing" means the acceptance checks the Problem lists: the unwritten-tests and runner-observer readiness gates, the unpassable-step control run and the contract check. Shape's other pre-publication checks are not added to Refine: the step self-check, the Decisions evidence gate, the optional decision check, the question gate and the `<slug>__<suffix>.js` naming rule. They judge intent prose, questions or package naming rather than a drafted acceptance. The step self-check's sentence-prefix rule would also refuse unchanged legacy packages that Refine explicitly allows. Refine keeps its own shared-step, binding-collision and topology checks.
- Constraint kept: no change to Shape's checks or their feedback; no new commands or flags; no timeout raised.
- Acceptance (request): synthetic projects and a scripted shaper. For each of Shape's checks, a refined draft that Shape would refuse for that reason is refused by Refine with the same reason, and a refined draft that passes them publishes. This is covered by the eight scenarios of acceptance.feature, with no live provider or network.

## Tests
- A refined draft whose failed scenario runs a named test absent before the Build is refused with Shape's unwritten-tests text, counts as invalid, and ends refinement_invalid with the draft unchanged: the `unwritten` journey, plus a Refine test in shape/refine_test.go (integration)
- A refined draft whose step rejects the runner's real passing output is refused with Shape's runner-observer text: the `observer` journey (integration)
- A refined draft with a step no implementation can pass is refused with Shape's unpassable-step text after the control run: the `unpassable` journey with a real Cucumber runner (integration)
- A refined draft with a confirmed contract contradiction is refused with Shape's contract text, and its identical resubmission is refused again without another review: the `contract` journey (integration)
- A refined draft with a confirmed environment finding is refused with Shape's environment text: the `environment` journey (integration)
- A refinement that passes every check publishes after one refiner request, and the force goldens stay byte-identical: the `plain` journey and the existing force golden tests (regression)
- Ordinary missing-feature red in a refinement is returned as readiness observations and published on acknowledgment, not refused: the `red` journey and the existing red Refine tests (regression)
- A refusal is repairable in the same run: a corrected submission is checked again and published: the `repair` journey (integration)
- The external refiner receives the refusal text as its round feedback: a test with the scripted external executor in shape/lineup_shape_test.go or shape/refine_test.go (integration)
- The original draft's own readiness is not judged, and unchanged red originals are still acknowledged: the existing Refine tests pass unchanged (existing)
- Shape's checks, texts and events are unchanged: the existing shape tests pass unchanged (existing)

## Feasibility
- Session evidence (my own scratch runs on a copy of HEAD fd8125a outside the checkout, not Kogen probe records), with Go 1.27.2, Node v24.21.0 and Kogen's Cucumber: the submitted harness compiled through the overlay in about 2 s with a warm build cache. Shape refused each defective draft with the expected headline. Unchanged Refine returned ordinary observations and published the `unwritten`, `observer`, `unpassable` and `environment` drafts after an acknowledgment, and published the `contract` draft at once with no contract request. So those five journeys and `repair` fail on the missing checks, while `plain` and `red` pass. The whole feature ran in about 35 s (6 failed, 2 passed). In the `unpassable` journey, Refine's observations showed the stub's `Error: coverage incomplete: this step is a stub` failure. Shape's item was `acceptance.feature line 3: Then is-even: the coverage is complete (step definition "is-even: the coverage is complete", features/steps/is-even__steps.js line 3): no pass is reachable: ...`.
- The observer controls printed `accepted` (exit 0) for good and `rejected` (exit 1) for bad. The bad run fails on the unwritten journey's feedback, exit and draft assertions.
