# Restore a same-value-aware decision check

Slug: k-shape-decision-same-value
Model: not applicable — one stateless check per checked submission maps the model's items to verdicts, an event and feedback lines; no retained state, retry or interacting rule is added beyond the existing submission attempts
Acceptance:

- features/steps/k-shape-decision-same-value__harness.js

Request (kogen-shaping, shelf request of 3 Nov 2026): the decision check compares each stated decision and each explicit example result in a candidate Intent with the request. It returns follows, contradicts or unsupported, and every verdict other than follows (unless the line is marked) sends the shaper back with feedback. The check was told only that contradicts means "the request states otherwise". So a decision that restates a request value in another notation could come back as contradicts. Examples are 1,000 and 1000, 0.5 and 50%, 2 minutes and 120 seconds, a date in another layout, a reordered list of the same items, and different letter case where case does not matter. The shaper then rewrites a correct decision, marks a plain restatement as an assumption, or asks a question with no real ambiguity behind it.

Current state of the code: this checkout has no decision check. Commit f04edce (Intent k-shape-drop-optins) deleted `shape/decision.go` and everything only it used when the `shape_decision_check` opt-in was removed. Today Shape never asks a model to check Decisions against the request. The request's line references (shape/decision.go:19-27 and :122-124) point at that deleted file.

After this change, `kogen intent shape` (packages `shape` and `cmd/kogen-shape`) always runs the decision check on Shape's files submissions, with no option, flag, setting or environment variable. It runs for the native shaper and for a claude-code shaper. Contradicts is now given only when the Intent's value and the request's value differ after the obvious normalisation of notation. A restatement of the same value follows the request and produces no feedback. A contradicts item that reaches the shaper names both values and what makes them differ. Kogen does not present a contradicts item as a contradiction unless it names both values, found where it says they are, and the two values still differ after Kogen's own digit-grouping normalisation. Genuinely different values (a different number, a wrongly converted unit, a different order where order matters) are still contradicts. A check that finds no contradicts item makes no extra model request; in fact every check makes exactly one.

Out of scope and unchanged: Refine (it runs no decision check); the automatic assumption marking of the old check (`markAssumptions` and the `decision_assumptions_marked` event are not restored); every prompt under shape/prompts, `ShaperInstructions`, the Refine prompt, the shaper and Refine tool definitions, `externalNote`, and the policy and force goldens (shape/testdata/*golden*.json), byte for byte; go.mod and go.sum; kogen-coordinator (`project.Config.ShapeDecisionCheck` and `project.DecisionCheck` stay unread); this repository's `.kogen/project.yaml`; and the files of earlier Intents.

## Decisions
- Restore the decision check and run it always, with no setting: k-shape-drop-optins deleted it under the owner's remove-now ruling, but this request presumes the check runs and asks only how its verdicts behave. (evidence: .kogen/intents/k-shape-drop-optins/intent.md; shape/shape.go; shape/decisions.go) (assumption: the request may predate that removal; restoring the check always on reverses the k-shape-drop-optins decision that Shape runs no decision check, adds one model request or executor session per checked submission, and its "no decision check request" assertions in features/steps/k_shape_drop_optins_test.go.txt no longer hold; reject this Intent at approval to keep the check removed) (source: request)
- Placement and route: the check runs in Shape's `checkSubmission`, on every files submission that passes the evidence gate (`evidenceGate`), before the step self-check, as the deleted check did. With the native shaper, it is one provider request through the shape role with instructions, one user message and exactly one tool, `submit_decision_check`. It prints the progress line `kogen: checking the stated decisions` and then a response line `kogen: decision check response <usage> wall_ms=<n>`. With a claude-code shaper, it is one fresh read-only executor session per check (`startExternal`, directory `<evidence dir>/executor-decision-<n>`), with the instructions plus the input as its brief and the schema below as its structured result. Its usage counts in the usage line: claude-code rounds are added to the round count, and native usage is added to the summed usage. Refine runs no decision check. (evidence: shape/shape.go; shape/question.go) (source: request)
- The check's user input is exactly `Slug: <slug>\n\n# Request\n\n<request>\n\n# Candidate intent.md\n\n<the written intent.md>`. `<request>` is the request text Shape holds (`sh.request`). (evidence: shape/shape.go) (source: request)
- `submit_decision_check` takes a strict schema: `{"items": [item]}`. Each item is an object with exactly these fields, all required: `statement` (string), `request_quotes` (array of strings), `verdict` (`follows`, `contradicts` or `unsupported`), `intent_value` (string), `request_value` (string), `difference` (string) and `why` (string); `additionalProperties` is false. A payload that is not an object with an `items` list of such items fails with class `shape`, reason `decision_check_invalid` and the detail `the decision check answer is not a valid submit_decision_check payload (<why>); nothing was published` (exit 1). A native answer without exactly one `submit_decision_check` call fails the same way. (source: request)
- The instructions keep the deleted check's text, except that they define the verdicts as follows (the request states the same value), contradicts (the request states a different value) and unsupported (the request does not state it), and list the three new fields. They also contain these three sentences verbatim, each on its own line. First: `Compare values, not notation: before comparing, normalise digit grouping (1,000 and 1000), percentages and fractions (50% and 0.5), units of the same quantity (2 minutes and 120 seconds), date layouts, the order of a list whose order does not matter, and letter case where case does not matter.` Second: `A statement that restates the request's value in another notation follows the request.` Third: `Give contradicts only when the values still differ after that normalisation, such as a different number, a wrongly converted unit or a different order where order matters; then give intent_value (the value as the statement writes it), request_value (the value as a request quote writes it) and difference (what makes them differ). For follows and unsupported give these three as empty strings.` (source: request)
- Kogen's rules for each item, in this order. (1) If the statement is not found in the candidate intent.md, or any of its request quotes is not found in the request, the item becomes unsupported. Finding uses `containsNormalized`. (2) A contradicts item stays contradicts only when all of these hold: `intent_value` is not blank and is found in the statement; `request_value` is not blank and is found in at least one of the item's request quotes; and the two values still differ after notation normalisation. If both values are named and found but equal after normalisation, the item becomes follows. If either value is blank or not found, the item becomes unsupported. (3) Notation normalisation is `normalizeWhitespace`, followed by removing every comma that has a digit just before it and exactly three digits just after it, where the third digit is not followed by another digit. Case is kept. So `1,000` and `1000` are equal; `10,000` and `1,000` differ; `1,5` and `15` differ. (4) follows and unsupported items keep their verdict. (5) An item whose statement carries `(assumption:` or `(evidence:` produces no feedback. (source: request)
- Event: each check records `{"event":"decision_check","follows":<n>,"contradicts":<n>,"unsupported":<n>,"items":[...]}` in the run's events. Each item is recorded with its final verdict and its statement, request_quotes, intent_value, request_value, difference and why. (source: request)
- Feedback: every item that is not follows and not marked is a problem. With at least one problem, the submission is refused (`sh.refused("decision_check", <problem lines>)`, an invalid outcome) and the shaper receives these lines joined by newlines, in order. First, the deleted check's headline: `Decision check: <n> stated decisions are not supported by the request; follow the request, cite the repository evidence that decides it with (evidence: ...), or mark the decision as an assumption the user must confirm:`. Second, its assumption rule: `Mark an assumption with (assumption: <what the user must confirm>) before the required trailing tag, e.g. - <decision> (assumption: <what the user must confirm>) (source: request); every Decision line keeps its trailing (source: request) or (source: answer N).`. Then one line per problem. An unsupported problem is `statement: <statement> | request_quotes: "<q1>", "<q2>" | verdict: unsupported | why: <why>`. A contradicts problem is `statement: <statement> | request_quotes: "<q1>" | verdict: contradicts | intent_value: <intent_value> | request_value: <request_value> | difference: <difference> | why: <why>`. With no problem, the submission goes on to the step self-check and readiness unchanged. (source: request)
- The acceptance harness relies on these existing test helpers keeping their names and signatures: `newShpFx`; the `shpFx` fields `Root`, `Stdout`, `Stderr` and `Prov` and its methods `setReport`, `shape`, `exists` and `read`; the `shpProvider` field `route` and method `allRequests`; and `shpStep`, `shpAnswer`, `shpCall`, `shpSubmit`, `shpToolNames`, `shpOutputs`, `shpBody`, `contractKind`, `shpScopedIntentMD`, `shpFeature` and `shpSteps`. A route answer takes precedence over any default answer the fake provider gives a decision check request. (evidence: shape/helper_test.go) (source: request)
- Tests are synthetic only, with no live provider, and use only owned child processes and temporary folders. (source: request)
