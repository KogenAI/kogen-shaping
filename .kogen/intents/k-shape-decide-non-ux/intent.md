# Decide non-UX shaping questions instead of asking

Slug: k-shape-decide-non-ux
Model: not applicable — one more check of a questions submission and one more gate on Decisions in the existing Shape submission path; the only new run state is a count of environment-only refusals
Acceptance:
- .kogen/intents/k-shape-decide-non-ux/acceptance.feature
- features/steps/k_shape_decide_non_ux_steps.js
- features/steps/k_shape_decide_non_ux_test.go.txt

K-SHAPE-DECIDE-NON-UX (Studio kogen issue ff6f8161-5ca9-4123-a635-89bc1c29d2b3, owner core principle relayed by kogen-main on 2 Nov 2026): shaping comes back to the user only for UI/UX questions the user has not already answered. Every technical, product-policy or environment ambiguity is investigated and probed by the shaper, then decided by it and recorded as a sourced Decision, with no question. On the AoR hill-climb 29 shapes stopped at questions_pending. saas-billing went 16/16 with 39 questions in total, each with its own recommended option and each asked after 0 repository probes, although the repository already has a `comped?` stub that answers one of them. Research classified 70 questions from 35 AoR questions_pending cells: 2 are UI/UX (whether a comment reaction is blocked beyond 16 characters or rejected with an error on submit), 68 are not (policy 58, environment 6, repo fact 1, other 3). 67 of 70 offered a "(recommended)" option, and only 11 of 70 were probed first.

Today Kogen's Shape (`shape/shape.go`) publishes every questions submission that passes the envelope check (only an explicit `kind` other than `product` or `handoff` is rejected), and the shaper's prose instructions alone ask it to keep to UI/UX questions. This change adds, in kogen-shaping only, a model-classified **question check** on every Shape questions submission (native and external). Questions classified `ui_ux` or `handoff` reach the user exactly as today. Any other class refuses the whole submission with feedback that tells the shaper to investigate and decide. A Decisions line can cite what was read or run with an **`(evidence: ...)` marker**, which a new model-free Shape gate checks against the repository and the shaping's own probes. Environment questions end as a "proceed without it" Decision or, asked again alone, as an `environment/shape_environment` fault, never as a question. The opt-in decision check stops telling the shaper to ask. No CLI command, flag, option or configuration key is added, and no timeout, limit or retry is added or raised. The question check uses the existing shared invalid-submission budget. The native shaper's instructions, its tool list, ordinary native request bytes, the external shaper's session text, Refine, init, approval, readiness and the other gates are unchanged.

## The question check
- Where: in `submitOne` (`shape/shape.go`), for every Shape submission with `questions`, native and external. It runs after the existing envelope validation (`validateQuestions`, including its explicit-kind rejection) and after the request audit gate when that is enabled, and before anything is saved or printed. There is no configuration key; it always runs. Refine, init, Shape workers, the contract review and confirmation, the request audit and the decision check make no question check, and a files or blocked submission makes none.
- Native Shape: one fresh read-only provider request, built like the decision check's: `Instructions` exactly the text below, `Input` one user message whose content is the input text below, `Tools` exactly the one definition below, its own conversation identity (`startConversation(sh.ev, "question-check")`), the call recorded with `BeginCall(..., "question check", ...)`, and progress lines `kogen: checking the questions` and `kogen: question check response <usage> wall_ms=<n>`. Its tokens are added to the Shape usage line's totals like the decision check's. A provider error ends Shape through the existing `providerFailed`. The response must be exactly one `submit_question_check` call.
- External Shape (`executor: claude-code`): one fresh read-only session through `startExternal`, in directory `<evidence dir>/executor-question-<n>` (n counts this run's question checks from 1), with stable text `<instructions> + "\n\n" + <input text>`, no dynamic text, the schema `parameters` below and one round. Its rounds count in the external usage line's round total. A round that does not finish is invalid with `the session ended without a result`, and a result that is not a JSON object is invalid with `not a JSON object`.
- The instructions, exactly (the acceptance fixture compares them):

```text
You check the questions a shaper wants to ask the user about one feature request. Only UI/UX choices that the request and the user's answers leave open, and mandatory authentication or security handoffs, may reach the user; the shaper investigates and decides everything else itself. You see only the request text, the earlier questions with the user's answers, and the questions. Read-only: do not use any tool except submit_question_check.

Give one item for every question: its number, one class and why (one short reason). The classes:
- ui_ux: a choice of what the user sees or does in the product's interface or interaction (layout, wording, flow, feedback, input behavior) that the request and the earlier answers leave open;
- handoff: a mandatory authentication or security step that only the user can perform, such as signing in or granting access;
- answered: the request or an earlier answer already settles it;
- technical: an implementation, architecture, library, protocol, data or testing choice;
- product_policy: a business, pricing, permission or other product rule that is not a choice of interface or interaction;
- environment: whether a tool, service, account, credential, network or other resource is available where the work runs;
- repository_fact: a fact that the repository's files, history or commands can establish.
Answer by calling submit_question_check.
```

- The input text: `Slug: <slug>` + `\n\n# Request\n\n` + the request exactly as received + `\n\n# Earlier questions and answers\n\n` + the rounds text + `\n\n# Questions\n\n` + the questions. The rounds text is exactly the `Round <k>:` text that `contextBlocks` (`shape/context.go`) puts under `# Your earlier questions and the caller's answers`, or `none` when the state has no rounds. The questions are, for each question in order, `<n>. <question>`, then one line per option `   <letter>) <label>` with ` (recommended)` appended for a recommended option, then `   kind: handoff` for a question of kind handoff. Lines are joined by single newlines, with nothing after the last. The two expected inputs are in the acceptance feature.
- The tool definition, compared semantically: `{"type":"function","name":"submit_question_check","strict":true,"description":"Submit the question check: one item per question with its number, class and reason.","parameters":{"type":"object","properties":{"items":{"type":"array","items":{"type":"object","properties":{"number":{"type":"integer"},"class":{"type":"string","enum":["ui_ux","handoff","answered","technical","product_policy","environment","repository_fact"]},"why":{"type":"string"}},"required":["number","class","why"],"additionalProperties":false}}},"required":["items"],"additionalProperties":false}}`.
- A valid answer has `items` as a list of objects, each with an integer `number`, a `class` from the enum and a string `why`, and exactly one item for each question number 1 to N, in any order. Native tool arguments decode integers as int64, and external results decode them as float64; both are accepted. Otherwise Shape ends with `shape/question_check_invalid: the question check answer is not a valid submit_question_check payload (<why>); nothing was asked` (exit 1), where `<why>` is `items must be a list`, `an item is malformed`, `expected one item for each question 1 to <N>`, `expected one submit_question_check call`, `the session ended without a result` or `not a JSON object`. Nothing is asked or saved.
- Every valid check records one event `{"event":"question_check","items":[{"number":n,"question":"<text>","class":"<class>","why":"<why>"},...],"asked":<count of ui_ux and handoff>,"refused":<count of the others>}`, with items in question order.
- When every question is `ui_ux` or `handoff`, the submission continues exactly as today: the state round, `questions.json`, the printed numbered block with `(recommended)` marks, exit 5, then answers by `<n>: <letter or words>` or `all: recommended`, with a resumed shaping that cites `(source: answer N)`.
- When at least one question has another class, nothing is asked: no round is saved, no `questions.json` is written, nothing is printed and the Shape run goes on. The submission is an invalid submission: one `submission_refused` event with gate `question_check` whose problems are the question lines, through the existing `refused`, counted on the shared invalid-submission counter. A mixed submission is refused as a whole, so its UI/UX questions may be submitted again once the others are decided. At the limit, Shape ends as today (`shape/invalid_output`, or `intent/not_ready` when files were written), except for the environment fault below. The feedback (the submit tool's result natively, the next round's feedback externally, followed there by the existing `\n\nCumulative proposal manifest: ...`) is the headline, then one line per refused question in question order, joined by single newlines with nothing after the last:
  - headline: `Question check: <R> of <N> question(s) are not UI/UX choices left to the user; nothing was asked. Investigate and decide each one yourself: read the repository or run a probe, then record a Decisions line that cites what you read or ran before its source tag, as - <decision> (evidence: <repository path>) (source: request) or - <decision> (evidence: ran `<command>`) (source: request). Ask the user only UI/UX questions that the request and the answers leave open, or a mandatory authentication or security handoff.`
  - question line: `- question <n> (<class>): <question text> | why: <why> | <instruction>`, where `<instruction>` is `decide it from what the repository and the request establish` for `technical`, `product_policy` and `repository_fact`; `the request or an earlier answer settles it; follow it and keep its (source: request) or (source: answer N)` for `answered`; and `do not ask about the environment; proceed without it and record that Decision, or, if the request cannot be shaped without it, submit only such environment questions again and Shape ends with an environment fault` for `environment`.
- Environment fault: a refused submission is environment-only when every one of its questions is classified `environment`. When an environment-only refusal is the second one in this Shape run, or the submission is the run's last allowed submission (the invalid count before it is the limit minus 1), its `submission_refused` event is recorded and Shape ends with `environment/shape_environment: shaping cannot go on without something only your environment can provide; nothing was asked or published` (exit 3). Its detail lines are `- <question text>` for each question of that submission. Nothing is asked or published, no question is pending, and files written by earlier attempts stay as they do after `intent/not_ready`.

## Decision evidence
- A `## Decisions` bullet line may carry one or more markers `(evidence: <citation>)` anywhere before its required trailing `(source: request)` or `(source: answer N)` tag. A marker starts at `(evidence: ` and ends at the first `)` outside a backtick-quoted span (or at the end of the line when there is none). The citation is one or more items separated by `; ` outside backticks. An item is either `ran `<command>`` (the word ran, a space and a backtick-quoted nonempty command) or a repository-relative path, optionally wrapped in one pair of backticks. A path ending in `/` is a directory.
- Gate: every Shape, native and external, in `checkSubmission` for a files submission, on the written and formatted `intent.md`. It runs after the data-stores gate and before the opt-in decision check, the step self-check and readiness. Decisions are numbered 1, 2, ... in the order of the section's `- ` lines (the section read as `decisionLines` does). Problem lines, in decision order and item order:
  - `- decision <n>: an empty (evidence: ...) item` for a blank item;
  - `- decision <n>: <path> is not a file or directory tracked at HEAD` when no file of `git ls-tree -r --name-only HEAD` equals the path, or, for a directory, starts with it;
  - native Shape: `- decision <n>: no probe of this shaping ran `<command>`` when no probe call of this Shape run had exactly that `command`;
  - external Shape, where Kogen does not see the commands: `- decision <n>: this shaping's session ran no command, so `<command>` was not run` when the shaper's session reported no completed, non-denied `Bash` tool (the `executor_tool` events that `inspectedBy` already reads).
- With at least one problem, nothing is published. The feedback is exactly `Decision evidence: <N> problem(s) with what the Decisions cite; nothing was published. A Decision's (evidence: ...) names files or directories tracked at HEAD, or ran `<command>` for a command this shaping ran, separated by "; ". Resubmitting this candidate unchanged is refused again.` followed by the problem lines, joined by single newlines with nothing after the last. It is an invalid submission with one `submission_refused` event, gate `decision_evidence`, on the shared counter. Accumulated proposals and written files stay as after other not-ready feedback, and the refused candidate reaches no step self-check, readiness or contract review. A candidate without markers, or with valid ones, continues exactly as today. Refine, `kogen intent approve` and the Intent lint do not check markers.
- Kogen checks that a cited file exists at HEAD and that a cited command ran in this shaping. It does not prove that the cited content supports the Decision, and on external Shape it cannot match the command text.

## Decision check (opt-in `shape_decision_check`)
- `decisionOutcome` and `markAssumptions` (`shape/decision.go`) treat a statement containing `(evidence:` like one containing `(assumption:`: it is not a problem and is not marked.
- Its feedback headline becomes `Decision check: <n> stated decisions are not supported by the request; follow the request, cite the repository evidence that decides it with (evidence: ...), or mark the decision as an assumption the user must confirm:`, with no "or ask". The rest of the decision check is unchanged.

## Decisions
- Shaping comes back to the user only for UI/UX questions the user has not already answered; every technical, product-policy or environment question is investigated, decided by the shaper and recorded as a sourced Decision, with no question (source: request)
- A non-UX ambiguity yields a probed, sourced Decision that cites what was read or run in the repository: an evidence marker on the Decision, checked against files tracked at HEAD and this shaping's probes (source: request)
- A genuine UI/UX preference the user has not answered still produces a question through the existing question/answer path, including `all: recommended` (source: request)
- The 6 environment asks end as "proceed without it" or an environment-fault outcome (`environment/shape_environment`, exit 3), never as a question (source: request)
- A mandatory authentication or security handoff (`handoff`) still reaches the user as today, since the request removes only technical, product-policy and environment questions (source: request)
- Regression cases are synthetic equivalents of the saas-billing trace: questions with recommended options asked after 0 probes, one answered by an existing `comped?` stub; the AoR task kits stay private (source: request)
- No new CLI command, flag or configuration key, no raised limits or timeouts; the question check uses the existing invalid-submission budget (source: request)
- Init's question about removing dependency-only protection is kept and Kogen's 01-project-setup.feature:115 is not changed, because a protection change is the user's decision (source: request)
- The item is built in kogen-shaping; changes another repository must make are follow-up items (source: request)
