# Send unprepared-environment steps back to shaping

Slug: k-shape-accept-env-prepare
Model: not applicable — one more finding kind in the existing stateless contract review gate; no new workflow state
Acceptance:
- .kogen/intents/k-shape-accept-env-prepare/acceptance.feature
- features/steps/k_accept_env_steps.js
- features/steps/k_accept_env_test.go.txt

Kogen runs acceptance in a fresh copy of the tree. A shaped acceptance step can fail on the unchanged tree only because that copy is not prepared for it. Examples are a store or schema that only the shaping checkout has, or Git history that the single-commit copy lacks. Today Shape offers such a failure to the shaper as legitimate missing-feature red to acknowledge. The Build then stops build_blocked as a protected-baseline contradiction. After this change, Shape sends such a step back to the shaper with its fresh-copy output, refuses the candidate and publishes nothing, so the step is corrected during shaping.

Readiness's existing dry run (`verify.Readiness.Check`, package kogen-verification, unchanged) is the run on the unchanged tree in Kogen's fresh-copy conditions. It materializes the candidate tree cold into a new repository with exactly one commit, holding only tracked files: no history, no ignored files, no dependency folders. It runs only the configured `commands.setup` there, then runs the acceptance command once. This item adds no second acceptance execution. It adds the judgement of why a scenario failed there to Shape's existing contract check (`shape/contract.go`), which already receives that run's observations. The check has three parts: the independent read-only review reports environment findings, Kogen evidences each one mechanically against that run's actual failure detail, and the independent confirmation confirms it. A confirmed environment finding refuses the candidate through the existing contract refusal route.

The behaviour is general to any stack: nothing matches Rails, Node or Git text. It is implemented only in kogen-shaping, without changes to kogen-verification or other component repositories. It adds no CLI command, flag or config key, and raises no timeout, bound or limit. The contract request and tool bounds, the submission retry limit, readiness and step-check limits all stay as they are. Contradiction findings, the acknowledgment of legitimate missing-feature red, step self-check, unwritten-tests and runner-observer gates and approval keep their current behaviour except where stated below.

### Review (`submit_contract_review`)
- The payload has exactly two fields, both required in the strict schema: `findings` (contradictions, unchanged item shape) and `environment`, a list of objects with exactly `scenario` (string), `output` (string) and `why` (string). The default no-finding answer is `{"findings":[],"environment":[]}`. A payload without `environment`, with other fields, or with a wrongly typed environment item is invalid. It ends the check `incomplete` and the candidate goes on, as invalid payloads do today.
- `contractReviewInstructions` adds this rule: report an environment finding for a scenario that failed in the readiness observations because Kogen's fresh copy was not prepared for the step, not because the requested behaviour is missing. Examples are a store, schema or other state that neither the steps nor the configured setup create, or Git history, ignored files or other state that only the shaping checkout has. The finding gives the scenario name exactly as in acceptance.feature, `output` copied exactly from that scenario's failure in the readiness observations, and why. The existing sentence "A scenario that fails only because the requested feature is missing is not a finding" stays.

### Evidence (Kogen alone)
An environment finding is evidenced only when all of these hold:
- `why` is not blank.
- The whitespace-normalized `scenario` equals the name of a scenario whose status is `failed` in this candidate's readiness result (`sh.ready.Scenarios`).
- The whitespace-normalized `output` is not blank and is contained in that same scenario's failure detail (`ScenarioResult.Detail`, whitespace-normalized).

A finding for a passed or unknown scenario is not evidenced, nor is output that appears only in another scenario's detail or in an earlier candidate's run. Findings that are not evidenced are never sent to confirmation and never refuse. With no evidenced finding of either kind, the check is `clean` and makes no confirmation call, as today.

### Confirmation (`submit_contract_confirmation`)
- The payload is unchanged. "Findings to verify" lists the evidenced contradictions first, numbered and formatted as today. The evidenced environment findings follow, continuing the numbering, each as `N. scenario: <scenario> | fresh-copy output: <output> | why: <why>` (values whitespace-normalized). Verdicts are counted by number exactly as today across both kinds; a finding without a counted verdict is refuted.
- `contractConfirmationInstructions` adds this rule: for an environment finding, answer confirmed only when the cited fresh-copy output shows that the step failed because the copy was not prepared for it, not because the requested behaviour is missing.

### Refusal
- One or more confirmed environment findings refuse the candidate exactly as confirmed contradictions do. The gate is `contract_review`. The refusal is kept per package hash, so resubmitting the same candidate is refused again without another review. It counts toward the existing submission retry limit, records `submission_refused`, and produces no acknowledgment offer and no publication. When Shape ends not ready on this refusal, the lines go to the existing `contract-contradictions.json` record, so `kogen intent approve` refuses that package hash with its existing error.
- The feedback has the existing contract headline and lines when contradictions were confirmed. Then, when environment findings were confirmed, it has the headline below with `%d` set to their number (contradictions first when both are present):
  `Environment check: %d acceptance step(s) fail on the unchanged tree because Kogen's fresh copy is not prepared for them, not because the requested behaviour is missing; nothing was published. Kogen runs acceptance in a fresh single-commit copy of the tree, without history or ignored files, after only the configured setup: make the step prepare the state it needs itself or in an earlier step of its scenario, or stop depending on state that copy lacks; do not delete or weaken a scenario to pass this check. Resubmitting this candidate unchanged is refused again.`
- Each confirmed environment finding then gets one line: `- <scenario> | fresh-copy output: <output> | why: <why> | confirmed: <confirmation why>` (values whitespace-normalized).
- The `contract_review` event keeps its fields. Its `findings`, `evidenced` and `confirmed` counts include both kinds. `result` is `refused` when anything was confirmed, else `clean`, or `incomplete` as today. Environment items are listed under a separate `environment` key with `scenario`, `output`, `why`, `evidenced`, `verdict` and `confirmation`.

### Example (the synthetic store fixture of the acceptance)
The checkout has an ignored, prepared `store/schema.json`, `setup: []`, and `accounts.js`, which prints `missing accounts schema` without that file. A step runs `accounts.js --active` in place. In the fresh copy the step fails with an assertion detail containing `missing accounts schema`. The review reports that output and the confirmation confirms it. The shaper gets `Environment check: 1 acceptance step(s) fail on the unchanged tree ...` with that output, not the acknowledgment text. The corrected step creates the store itself in a temporary directory. It then fails only with `unknown option --active` (the missing behaviour). A repeated environment claim quoting `missing accounts schema` is not evidenced against that new detail, so the correction is offered for acknowledgment and published.

## Decisions
- An acceptance step that needs prepared state gets it in the step itself or in the Intent's own scenario steps that run before it. The refusal tells the shaper exactly that. Kogen does not edit or prescribe `commands.setup`, which belongs to the protected project configuration. (source: request)
- The shape-time run is readiness's existing cold single-commit materialized copy with only the configured setup. It runs once, and no second acceptance execution is added. (source: request)
- An environment failure there refuses the candidate and returns the failing scenario with its actual fresh-copy output to the shaper. It is never offered for acknowledgment as missing-feature red. (source: request)
- Recognition is stack-general: Kogen matches no stack- or tool-specific text. The independent review and confirmation judge the cause, and Kogen checks the cited output against the real run. (source: request)
- No new CLI command, flag or config key; no raised timeout or limit. Regression tests are synthetic only, with no live provider or network. (source: request)

## Tests
- A confirmed environment finding refuses the candidate with the environment headline, scenario and fresh-copy output, never with acknowledgment, and the step-prepared correction is published: the protected `store` journey (regression)
- A step that depends on Git history the single-commit copy lacks is refused with its fresh-copy output and its corrected package published: the protected `history` journey (regression)
- An environment claim whose output is not in the current failing scenario's fresh-copy detail is not evidenced and does not refuse; legitimate behaviour red is still offered for acknowledgment: the second round of the protected `store` journey, plus `TestContractEvidenceRule` cases in shape/contract_check_test.go for a passed scenario, an unknown scenario, output only in another scenario's detail, and blank output or why (unit)
- The review payload requires exactly `findings` and `environment`, with exact environment item fields and types; the default no-finding answer becomes `{"findings":[],"environment":[]}`: update `TestContractPayloadValidation` and the scripted default in shape/helper_test.go (unit)
- Environment findings are numbered after contradictions in the confirmation input, counted by number, and formatted in the refusal (environment headline after the contract headline when both are confirmed); a refuted environment finding does not refuse: extend `TestContractFormats`, `TestContractVerdictCounting` and `TestContractCheckUnevidencedAndRefutedFindingsNeverRefuse` (unit)
- A not-ready end on an environment refusal writes contract-contradictions.json, and approval refuses that hash: extend `TestContractCheckKeptContradictionEndsNotReadyAndApprovalRefusesIt` with an environment-only case (integration)
- Contradiction findings, acknowledgment, the other readiness gates, CLI and limits are otherwise unchanged: existing shape tests and configured checks pass (existing)
