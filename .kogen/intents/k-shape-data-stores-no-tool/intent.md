K-SHAPE-DATA-STORES-NO-TOOL (regression of Kogen 816b0b0, reverted by 3742abe; Kogen issue 09096a6e reopened). Kogen 816b0b0 made shaping find where an entity's data lives: an optional `## Data stores` section of `intent.md`, a model-free scan of the files tracked in Git for each declared id-key spelling, a Shape gate that refuses a section leaving a referencing file uncovered, review evidence and a verdict rule, and a prose paragraph (`dataStoresGuidance`) appended to the shaper's instructions. Research screened 816b0b0 against its parent 514dab4 as 4 matched pairs on the same host at the same time, with native shaping on openai/gpt-6.1-terra medium and a request-only data-deletion task: the parent produced a valid Intent 4 of 4 times, 816b0b0 0 of 4 times. Every 816b0b0 shape was refused within 52-77 s with `forced_submit_turn`, `no_tool_turns` 3, "answered without calling any tool 3 times", so no Data stores section was written and the new scan and its gate never ran. The base hits the same refusal class in about 5 of 20 shapes elsewhere. The candidate cause is the new instructions paragraph pushing the model into prose turns. This is not proven (4 pairs, paired sign p = 0.0625).

This change re-lands the Shape half of K-SHAPE-DATA-STORES in kogen-shaping without that paragraph in the native shaper's instructions. The native shaper's instructions stay byte-identical to the current tree, which has 514dab4's shaping instructions. The scan instead becomes a model-free native tool, `data_stores`, that the native shaper calls with the id-key spellings. Its guidance lives in the tool's definition and in the tool's result, not in the instructions. Model-free material reaches the model only as an answer to a tool call. The `## Data stores` section, its scan and the Shape gate behave as in 816b0b0 on native and external Shape. External Shape (`executor: claude-code`) has no Kogen tools, so it gets the guidance paragraph in its own session text only, without the review clause. An ordinary request keeps native requests identical to the current tree except for the added tool definition. No new CLI command, flag, option or configuration key is added, and no timeout, limit or retry is added or raised. Refine, approval, readiness, the other gates, Build and review are unchanged.

## The `data_stores` tool (native Shape only)
- Offered on every request of the native main shaping conversation, after `documentation` and before `propose_files`. The tool list of an ordinary native Shape is exactly `read_file, view_image, list_files, search_text, probe, documentation, data_stores, propose_files, submit` (`shape_batch` follows when Shape workers are enabled). It is not offered to Refine, Shape workers, the contract review and confirmation calls, the request audit or the decision check. External Shape cannot call it.
- Its definition on the wire is exactly this JSON object (compared semantically): `{"type":"function","name":"data_stores","description":"Find where an entity's data lives. For a request about an entity's data (for example deleting, exporting or moving an account's data), call this with each spelling of the entity's id key before you write scope and acceptance. It lists every file tracked at HEAD that references a key and how intent.md's ## Data stores section covers each one.","parameters":{"type":"object","properties":{"keys":{"type":"array","items":{"type":"string"}}},"required":["keys"],"additionalProperties":false},"strict":false}`. The definition is built in the shape package (agent.Defs in kogen-executor is not changed).
- A call is an ordinary tool call: it is not a tool-free answer and does not count toward the no-tool limit. It is not a read, list or search inspection, so it does not change `inspected` or `shape/uninspected`. Its output is an ordinary function_call_output, through the existing `toolOutput`.
- Arguments: `keys` must be a nonempty array of strings, each nonempty, with no whitespace or backtick. Otherwise (missing, not an array, empty, a non-string, an empty string, whitespace or a backtick) the output is exactly `data_stores: keys must be a nonempty list of id key spellings without whitespace or backticks; nothing was scanned` and nothing is scanned. Duplicate keys are scanned once, in first-occurrence order.
- Output for valid keys: these lines joined by single newlines, with no trailing newline:
  1. `Data stores for keys <keys joined by ", ">: files tracked at HEAD that reference a key`;
  2. one line per reference of the scan below, in reference order: `- <file> references <key> (line <n>)` or `(lines <n>, <m>, ...)`; or the single line `- none` when there is no reference;
  3. exactly `Record them in a ## Data stores section of intent.md: a line - key `<key>` for each key, then, for each file above or a directory (a path ending in /) that holds some of them, either - `<path>`: in scope, observed by `<text>`, where acceptance.feature or a step file listed under Acceptance contains <text>, or - `<path>`: excluded by decision <n>, where line <n> of ## Decisions names <path> and keeps its source. Shape refuses a candidate whose section leaves one of these files uncovered.`
  On the acceptance fixture with key `account_id` the reference lines are exactly `- db/memberships.csv references account_id (line 1)`, `- exports/1.json references account_id (line 1)`, `- exports/2.json references account_id (line 1)`, `- lib/account.js references account_id (line 1)`, `- lib/exports.js references account_id (lines 1, 4)`.
- A Git failure of the scan (git grep status other than 0 or 1) is an error of the Shape run, as for the gate.

## The `## Data stores` section
- Optional. The section is the `- ` lines from the line `## Data stores` up to the next line starting with `#`. This is the same reading as the other sections (`sectionBullets` of kogen-coordinator's project/intent.go, which is unexported; the shape package reads the section the same way from the written `intent.md`). Other lines in it are ignored. An `intent.md` without a `## Data stores` line gets no data-store gate. `kogen intent approve` and the Intent lint do not check the section.
- Each `- ` line is exactly one of these forms (backticks literal, `<n>` a decimal integer of at least 1 without leading zeros):
  - `- key `<key>`` — a spelling of the entity's id key, `<key>` nonempty without backtick or whitespace. At least one is required.
  - `- `<path>`: in scope, observed by `<text>`` — `<path>` a repository-relative path, `<text>` nonempty without backtick.
  - `- `<path>`: excluded by decision <n>`.
  A `<path>` ending in `/` is a directory and matches every scanned file whose path starts with it. Any other `<path>` matches only the file with exactly that path.
- An item is valid when its conditions hold, checked in this order:
  1. At least one file tracked at HEAD matches its path.
  2. For `in scope`: `<text>` occurs in `acceptance.feature` or in a step file listed under `Acceptance:` (their contents on disk).
  3. For `excluded`: `## Decisions` has at least `<n>` bullet lines.
  4. For `excluded`: its `<n>`th bullet line contains `<path>` exactly as written in the item (trailing `/` included).
  Decisions keep their required `(source: request)` / `(source: answer N)` tag as today.

## The scan (shared by the tool and the gate)
- Keys are scanned in their given order (the tool) or in section order (the gate), each once. The references of a key are the files tracked at HEAD, outside `.kogen/`, whose content contains the key with no letter, digit or underscore immediately before or after it. Binary files are skipped. This is exactly what `git grep -I -n -w -F -e <key> HEAD -- . ':(exclude).kogen'` reports, with the 1-based numbers of the lines that contain the key. On the acceptance fixture, `my_account_id` and `account_ids` (lib/notes.txt) are not references of `account_id`, `.kogen/notes.txt` is excluded, and `exports/<account_id>.json` (lib/exports.js line 1) is a reference.
- A reference is (file, key, lines), ordered by file path (byte order), then by key order. The gate counts a reference as covered by the first valid item, in section order, whose path matches its file.
- The scanned commit is `HEAD`. The candidate's own new files are not at HEAD and are not scanned. A section without a valid key line produces no references.
- Line numbers are written `(line 1)` for one line and `(lines 1, 4)` for several, joined by `, ` in ascending order.

## Shape: the data-stores gate
- Where: every Shape, native and external, in `checkSubmission` (`shape/shape.go`), for a files submission whose written and formatted `intent.md` has a `## Data stores` line. It runs after the fixers and the existing contract-refusal check of an unchanged refused candidate, and before the opt-in decision check, the step self-check and readiness. Refine runs no data-store gate.
- Problems, in this order, each one line:
  1. `- ## Data stores declares no key` when the section has no valid key line;
  2. for each `- ` line that is none of the three forms, in section order: `- not a ## Data stores item: <the line as written>`;
  3. for each invalid item, in section order, its first failing condition: `- <path>: no file tracked at HEAD has this path`, `- <path>: acceptance.feature and the step files listed under Acceptance do not contain <text>`, `- <path>: ## Decisions has no line <n>`, `- <path>: decision <n> does not name <path>`;
  4. for each uncovered reference, in reference order: `- <file> references <key> (line <n>)` or `(lines <n>, <m>, ...)`, followed by `; no ## Data stores item covers it`.
- With at least one problem, nothing is published for this submission. Its feedback is the tool result for native Shape and the next round's feedback for external Shape, followed there by the existing `\n\nCumulative proposal manifest: ...`. The feedback is exactly the headline
  `Data stores: <N> problem(s) with where the data of the declared keys lives; nothing was published. Every file tracked at HEAD that references a key declared under ## Data stores needs an item that covers it: in scope, observed by text that acceptance.feature or a listed step file contains, or excluded by a numbered Decision that names it. Resubmitting this candidate unchanged is refused again.`
  (N = number of problem lines), followed by the problem lines, joined by single newlines with nothing after the last. For the acceptance fixture's package that covers only `db/memberships.csv` and `lib/account.js`, the lines are exactly `- exports/1.json references account_id (line 1); no ## Data stores item covers it`, `- exports/2.json references account_id (line 1); no ## Data stores item covers it` and `- lib/exports.js references account_id (lines 1, 4); no ## Data stores item covers it`.
- It is an invalid submission: one `submission_refused` event with gate `data_stores` whose problems are the problem lines, through the existing `refused`. It counts on the shared invalid-submission counter. Accumulated proposals stay, and the written files stay as after other not-ready feedback. The refused candidate reaches no step self-check, readiness or contract review, supplies no readiness evidence and is never acknowledgeable. An unchanged resubmission is refused again with the same text. At the third invalid submission Shape ends as today with `intent/not_ready: the Intent is not ready to build` and the problem lines (exit 1).
- A candidate with a section and no problems continues exactly as today (step self-check, readiness, contract review, acknowledgment).

## Unchanged and out of scope
- Review (the Data stores evidence in the review authority and the verdict rule refusing an approval while a file is uncovered) lives in kogen-build. The reviewer prompt paragraph lives in kogen-executor. Sharing the scan with review (for example by moving it into kogen-coordinator's project package) needs those repositories too. Each is a follow-up item, not part of this one. Until then the external paragraph and the tool result do not claim that review checks the scan.
- Measuring the outcome on the research reproduction pack (kogen-bench 541b9e76 reproduce/kogen-shape-data-stores-816b0b0, openai/gpt-6.1-terra medium) is not part of this Build or its acceptance: the pack is private and the lane is a paid, nondeterministic model. Neither Shape nor the Build ran the shaper with and without the 816b0b0 guidance on that lane. What is established here is by construction: the native instructions are byte-identical to the base that measured 4 of 4, and only the tool definition is added. Whether the added definition itself changes the no-tool refusal rate on that lane is untested. Research re-measures it on the pack after landing.
- Kogen cannot tell mechanically that a request concerns an entity's data. The tool runs when the shaper calls it and the gate when the section is present. Detection is not exhaustive. Coverage is per file, so a file holding several stores is one item.
- The Build updates the tests and goldens that pin the native tool list or ordinary request bytes to the added definition: for example `TestShapeOneShotWritesThePackageAndPrintsTheLines`, `TestShapeBlockedReportIsPrintedAndWritesNothing`, `TestShapeBatchRunsWorkersAndReturnsTheirResults`, `TestProposeFilesStagesPackage`, `TestProposeFilesNativeOnly` and `TestShapeForceWireCompatibility` with `shape/testdata/force_ordinary_golden.json`.
